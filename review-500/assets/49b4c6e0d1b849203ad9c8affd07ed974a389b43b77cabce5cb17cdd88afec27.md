# Kilnbrook July scheduler automation contract

This file is the local contract for the offline scheduler. The implementation must use Python 3.11, the standard library, and `openpyxl` only. It must not use network access, a clock, randomness, macros, or external services.

## Interfaces

The package exposes this exact callable:

```python
plan(bookings_path, turnaround_path, crew_path, bays_path, policy_path, objective, output_path) -> dict
```

Arguments are positional-or-keyword filesystem paths. `objective` is normalized by trimming and case-folding and must then be exactly `coverage` or `cost`. Any other value raises `ValueError`. The module-level `DEFAULT_OBJECTIVE` is exactly `coverage`; the supplied July workbook and bundled summary are generated with that default.

The command-line interface is:

```text
python build_schedule.py --bookings PATH --turnaround PATH --crew PATH --bays PATH --policy PATH --objective {coverage,cost} --output PATH --summary PATH
```

The CLI calls the same `plan` function and writes the returned dictionary as UTF-8 JSON to `--summary`. Both output files are replaced only after successful validation and schedule generation.

## Input workbooks

Each workbook has one required worksheet. The parser locates the header row by its required field names, so title and blank rows above the table are allowed. Header matching trims whitespace and ignores case; field names themselves are not governed labels. Optional `Notes` columns may be absent or contain any value.

### `cranemoor_updated_bookings.xlsx`, sheet `Bookings`

Required columns are:

| Column | Meaning |
|---|---|
| `Booking ID` | Source identifier; nonblank and preserved exactly in output |
| `Revision` | Nonnegative integer revision used for reconciliation |
| `Status` | One of the policy status aliases |
| `Operation Date` | Calendar date |
| `Requested Start` | Local time, or an explicit datetime for a cross-midnight operation |
| `Operation Duration (minutes)` | Positive numeric minutes |
| `Equipment Class` | One of the policy equipment aliases |
| `Required Crew Count` | Positive integer |
| `Required Certifications` | Semicolon-delimited required tokens; blank means no required token |
| `Priority` | Nonnegative integer |

Optional columns are `Notes`, `Requested End`, `Requested Pre-turnaround (minutes)`, `Requested Post-turnaround (minutes)`, and `Requested Bay Class`. When `Requested End` is supplied, it must be strictly after `Requested Start` and exactly agree with the end calculated from the governed duration. Booking-side turnaround and bay values are legacy/requested information only and never override the frozen snapshot.

For a booking, requested operation end is requested start plus duration. The operation date identifies scope even if occupied time crosses midnight.

### `turnaround_snapshot_2026-06-01.xlsx`, sheet `Turnaround`

Required columns are `Equipment Class`, `Pre-turnaround (minutes)`, `Post-turnaround (minutes)`, and `Compatible Bay Class`. Each normalized equipment class has one governed lookup row; exact repeated rows are collapsed and conflicting rows raise `ValueError`.

### `kilnbrook_crew_roster.xlsx`, sheet `Crew Roster`

Required columns are `Employee ID`, `Employee Name`, `Date`, `Shift Start`, `Shift End`, `Certifications`, and `Hourly Rate`. `Notes` is optional. A roster row with blank or absent `Certifications` is retained in data quality reporting but is ineligible for every assignment. Exact repeated availability rows collapse; rows with the same natural key `(Employee ID, Date, Shift Start, Shift End)` but conflicting governed values raise `ValueError`.

### `kilnbrook_bay_calendar.xlsx`, sheet `Bay Calendar`

Required columns are `Bay ID`, `Bay Class`, `Date`, `Window Start`, `Window End`, and `Availability`. Availability aliases are the policy's available/open/operating labels or blackout/unavailable/closed labels. A row marked available is an operating window; a row marked blackout is an unavailable period. Exact repeated rows collapse. Conflicting rows with the same `(Bay ID, Date, Window Start, Window End)` key raise `ValueError`.

Rows that cannot affect the July plan because their date is outside the planning window may be retained as source records and are not used for capacity. Required key fields still must be present. Optional notes have no validation or eligibility effect.

Time-only shift and bay window endpoints are on the row's `Date` and must have an end later than their start. A cross-midnight shift or bay window may use an explicit ISO datetime for its end on the following date; its start must still fall on the row's `Date`.

## Reconciliation and validation

All five input paths are checked for presence before any output path is read, changed, or created. A missing path raises `FileNotFoundError` naming the source filename. A present workbook missing its required sheet, header, or field raises `ValueError` naming the source and missing element.

Booking records are grouped by source `Booking ID`. The greatest valid revision controls. Lower revisions are superseded and are never scheduled or counted. Identical rows at the controlling revision collapse; conflicting governed fields at that revision raise `ValueError` identifying the booking. Notes and legacy/requested turnaround fields are non-governing and do not create a duplicate conflict.

After controlling rows are selected, cancelled and out-of-window rows are excluded from demand and recorded in the workbook's `Data Quality` section. Governed fields on controlling in-scope confirmed/provisional rows are validated before scheduling. Unknown status, equipment, bay, availability, certification, or objective labels raise `ValueError`; normalization is trim plus case normalization and the finite aliases stated in the policy only. Negative governed values and invalid time order raise `ValueError` with the source and field. No partial output may remain after a validation failure; a pre-existing output must remain byte-for-byte unchanged.

## Scheduling model

The frozen turnaround lookup supplies pre-turnaround minutes, post-turnaround minutes, and compatible bay class. Any booking-side legacy values are ignored for these calculations.

```text
operation_end = requested_start + operation_duration
occupied_start = requested_start - frozen_pre_turnaround
occupied_end = operation_end + frozen_post_turnaround
```

Occupied intervals are half-open. Every assigned employee must have a nonblank certification record, hold every required certification token, and have a shift fully containing the complete occupied interval. Every booking receives exactly its required number of distinct employees. A bay must have the compatible normalized class, a fully containing operating window, and no overlapping blackout. Employees and bays cannot have overlapping occupied intervals. The number of concurrently active assigned employees, including turnaround-only time, cannot exceed the policy cap.

For each employee-booking assignment, occupied duration is independently rounded upward to a quarter-hour. An exact quarter-hour is unchanged. Rounded hours are multiplied by that employee's governed hourly rate; totals are summed without whole-hour intermediate rounding.

## Daily capacity

Return one daily record for every planning-window date. `scheduled` is the number of selected bookings whose operation date is that date. `available_bay_hours` is calculated separately for each bay as the union of that date's operating windows less the union of overlapping blackout periods, then summed across bays; overlaps are never double-counted. `used_bay_hours` is the sum of selected occupied bay intervals clipped to that calendar date, including turnaround and any midnight split, once per booking rather than once per crew member.

## Objectives

In `coverage` mode, the candidate set is every in-scope confirmed or provisional booking. Select a globally feasible schedule with this lexicographic objective, in order:

1. Maximize scheduled booking count.
2. Maximize the sum of booking priorities.
3. Minimize total labour cost.
4. Minimize the lexicographically ordered assignment signature.

In `cost` mode, provisional bookings are left unscheduled with reason `NOT_SELECTED`. Among confirmed bookings, select a globally feasible subset with this objective:

1. Maximize scheduled confirmed-booking count.
2. Minimize total labour cost.
3. Maximize the sum of booking priorities.
4. Minimize the lexicographically ordered assignment signature.

The assignment signature is a tuple of rows sorted by `(Booking ID, Bay ID, Employee IDs)`, where each row is `(Booking ID, Bay ID, sorted Employee ID tuple)`. It is compared lexicographically. This makes all ties deterministic and independent of source row order.

## Unscheduled reason codes

Each eligible booking not selected receives exactly one reason, using this precedence when more than one condition applies:

```text
NO_CERTIFIED_CREW
NO_COMPATIBLE_BAY
CREW_UNAVAILABLE
RESOURCE_CONFLICT
STAFFING_CAP
NOT_SELECTED
```

`NO_CERTIFIED_CREW` means fewer distinct eligible certified employees exist than the required crew count. `NO_COMPATIBLE_BAY` means no compatible bay can contain the occupied interval after blackout checks. `CREW_UNAVAILABLE` means certified employees exist but no required-size crew can cover the complete occupied interval. `RESOURCE_CONFLICT` means an individually feasible assignment is blocked by the selected schedule's employee or bay occupancy. `STAFFING_CAP` means an individually feasible assignment is blocked only by the concurrent headcount cap. `NOT_SELECTED` is used for provisional demand in cost mode. Cancelled and out-of-scope rows are quality dispositions, not unscheduled demand.

If no feasible option exists in isolation, the first applicable diagnostic in the listed order is used. For a booking that has an isolated feasible option but is omitted from the selected global schedule, resource overlap is reported before staffing-cap pressure when both apply.

## Return schema

The returned dictionary has exactly these keys and is JSON-serializable:

```json
{
  "objective": "coverage",
  "scheduled_booking_ids": ["..."],
  "unscheduled": [{"booking_id": "...", "reason": "..."}],
  "total_labor_hours": 0.0,
  "total_labor_cost": 0.0,
  "booking_coverage": 0.0,
  "daily_capacity": [
    {"date": "2026-07-01", "scheduled": 0, "available_bay_hours": 0.0, "used_bay_hours": 0.0}
  ]
}
```

Booking IDs and unscheduled records are sorted by booking ID. Daily records contain every date in the July planning interval in ISO order. Numeric hours use three decimal places, cost uses two, and coverage uses four. A structurally valid zero-row booking table produces an empty schedule and zero totals, with zero coverage when its denominator is zero.

## Workbook sections

`kilnbrook_july_capacity.xlsx` contains the visible sections `Run Summary`, `Schedule`, `Unscheduled`, `Daily Capacity`, `Data Quality`, and `Assumptions`. The summary names the selected objective and recommendation explicitly as either greatest booking coverage or lowest labour cost. Schedule rows retain source booking, bay, and employee identifiers and show requested and occupied intervals. Assignment rounded hours and labour cost are formulas driven by visible occupied duration and rate cells. Scheduled count, labour hours, labour cost, coverage, and daily capacity roll-ups are formulas linked to detail cells. Data-quality dispositions show reconciliation, normalization, cancellation/scope exclusions, duplicates, and ineligible blank-certification rows encountered in the run.
