# 试玩覆盖分析：Godot 4.4 输入传播与暂停机制验证

> 本文档为 Alpha 阶段线下集中试玩设计，核心目标是验证 Godot 4.4 引擎底层的输入事件传播与暂停机制在真实玩家操作下的表现。依据来源为作者中文知识摘要（取证 2026-10-20），非官方完整译文。

---

## 1. 测试目标概述

本次试玩不以验证原生按键映射或库存内容为重，而是聚焦于以下两个引擎底层机制在复杂游戏场景中的实际行为：

1. **输入事件传播路径**：`_input` 与 `_unhandled_input` 的调用顺序、GUI 层级对事件的消费与放行。
2. **暂停与处理模式**：`SceneTree.paused` 对物理系统的影响、`process_mode` 对节点行为的控制。

---

## 2. 输入事件传播覆盖设计

### 2.1 `_input` 与 `_unhandled_input` 的调用顺序验证

**引擎机制**：`_input` 先于 GUI 处理被调用；只有未被 GUI 消费的事件才会继续传递到 `_unhandled_input`。因此，游戏逻辑输入通常应放在 `_unhandled_input` 中，避免与 UI 冲突。

**试玩任务设计**：

| 任务编号 | 场景描述 | 验证目标 |
|---------|---------|---------|
| IN-01 | 玩家在解谜界面同时存在可点击按钮和角色移动区域 | 确认点击按钮时不触发角色移动（事件被 GUI 消费） |
| IN-02 | 玩家在菜单打开状态下按下动作键 | 确认动作键不触发游戏内攻击/互动 |
| IN-03 | 玩家关闭菜单后立即操作 | 确认事件恢复正常传播到游戏逻辑层 |
| IN-04 | 全屏半透明 UI 覆盖游戏区域时的按键操作 | 确认 `_input` 仍先收到事件，但 GUI 是否消费决定后续传播 |

**观察指标**：
- 在 `_unhandled_input` 中是否收到预期外的游戏动作事件。
- 玩家操作 UI 后是否意外触发了游戏内行为。

### 2.2 `accept_event` 与 `mouse_filter` 的交互验证

**引擎机制**：GUI 控件可使用 `accept_event` 主动消费事件，阻止其继续传播到 `_unhandled_input`。`mouse_filter` 属性决定控件对鼠标事件的处理方式——是接受、忽略还是穿透。

**试玩任务设计**：

| 任务编号 | 场景描述 | 验证目标 |
|---------|---------|---------|
| IN-05 | 装饰性图标覆盖在可交互按钮上方 | 确认装饰图标不拦截点击（需设置 `MOUSE_FILTER_IGNORE`） |
| IN-06 | 多层 UI 堆叠（血条、小地图、技能栏）时的点击测试 | 确认只有最上层可交互控件收到事件 |
| IN-07 | 输入框获取焦点后的键盘事件 | 确认输入法字符不触发游戏快捷键 |
| IN-08 | 拖拽操作跨越多个控件区域 | 确认 `mouse_filter` 设置正确时拖拽不会误触发下层控件 |

**观察指标**：
- 装饰元素是否意外拦截了玩家对下层按钮的点击。
- 多层 UI 叠加时点击目标是否与视觉层级一致。

## 3. 暂停与处理模式覆盖设计

### 3.1 `SceneTree.paused` 与物理系统

**引擎机制**：设置 `SceneTree.paused = true` 后，物理系统将停止模拟。这意味着暂停时角色不会因重力下落、碰撞体不会继续推挤。

**试玩任务设计**：

| 任务编号 | 场景描述 | 验证目标 |
|---------|---------|---------|
| PA-01 | 玩家在空中打开暂停菜单后恢复 | 确认角色不会在暂停期间因物理模拟而位移 |
| PA-02 | 玩家在移动平台上暂停，恢复后检查位置 | 确认平台与角色的相对位置在暂停前后一致 |
| PA-03 | 暂停时存在运动中的刚体，恢复后检查状态 | 确认刚体在恢复时继续运动而非突然加速 |

**观察指标**：
- 暂停恢复后角色/物体的位置是否与暂停瞬间一致。
- 是否存在暂停恢复后的"物理弹跳"或异常位移。

### 3.2 `process_mode` 的节点级控制

**引擎机制**：`process_mode` 决定节点在暂停时的行为：
- **Inherit**（默认）：跟随祖先节点的暂停状态。
- **Pausable**：随暂停停止处理。
- **Always**：暂停时仍然处理。

**试玩任务设计**：

| 任务编号 | 场景描述 | 验证目标 |
|---------|---------|---------|
| PA-04 | 暂停菜单中的动画/UI 效果 | 确认菜单节点使用 `Always` 模式，暂停时仍可交互 |
| PA-05 | 游戏世界中设为 `Always` 的背景粒子效果 | 确认暂停时背景特效仍在播放 |
| PA-06 | 设为 `Pausable` 的敌人 AI 节点 | 确认暂停时敌人完全停止行为 |
| PA-07 | 嵌套节点的 `Inherit` 传播测试 | 确认子节点正确跟随父节点的暂停状态变化 |

**观察指标**：
- 暂停菜单是否可正常交互（按钮可点击、动画可播放）。
- 游戏世界元素的暂停/恢复行为是否符合 `process_mode` 设定。

### 3.3 暂停时信号触发问题

**引擎机制**：即使场景树暂停，信号仍然可以触发。这意味着不能简单地将所有节点关闭来当作"菜单修复"——某些逻辑可能通过信号在暂停期间继续执行。

**试玩任务设计**：

| 任务编号 | 场景描述 | 验证目标 |
|---------|---------|---------|
| PA-08 | 暂停时触发计时器信号 | 确认计时器是否仍在暂停期间触发回调 |
| PA-09 | 暂停时网络状态变化信号 | 确认网络相关信号不会在暂停期间修改游戏状态 |
| PA-10 | 暂停前已连接的事件总线信号 | 确认全局事件不会在暂停期间传播到游戏逻辑 |

**观察指标**：
- 暂停期间是否有非预期的状态变化。
- 恢复后是否存在"丢失的信号"或"重复的信号"。

## 5. 数据收集方法

- **观察员记录表**：每个任务预设"通过/异常/不确定"三栏，观察员在玩家操作时实时标记。
- **屏幕录制**：每场全程录制，用于回放分析异常帧。
- **引擎日志抓取**：在关键节点添加 `print` 输出，记录 `_input` / `_unhandled_input` 的调用链和 `process_mode` 的实际状态。
- **玩家访谈**：每场结束后简短询问玩家是否遇到"操作不符合预期"的情况，定位潜在引擎行为问题。

## 6. 风险与局限

- 本覆盖设计基于作者中文知识摘要，非官方完整文档翻译。可能未涵盖引擎的所有边界情况。
- 试玩环境使用 Godot 4.4.1.stable，与摘要所基于的 4.4 分支可能存在细微差异。
- 部分任务（如 PA-08 计时器信号）可能需要额外脚本注入来观测内部状态。
