# 主持人/观察员说明：引擎特性观察重点与防坑指南

> 本指南面向参与线下试玩的观察员和场次主持人，提供在 Godot 4.4 引擎特性层面的具体观察重点与注意事项。依据来源为作者中文知识摘要（取证 2026-10-20），非官方完整译文。

---

## 1. 本次测试的核心定位

**重要**：本次试玩的目标是验证引擎底层的输入传播与暂停机制，**不是**验证原生按键映射迁移或重复库存内容。

观察员应聚焦于以下两类问题：
- 玩家操作是否触发了非预期的游戏行为（输入传播异常）。
- 暂停/恢复后游戏状态是否出现不一致（暂停机制异常）。

---

## 2. 输入事件传播：观察重点

### 2.1 `_input` vs `_unhandled_input` 的观察时机

**引擎行为**：`_input` 回调先于 GUI 处理执行；只有未被 GUI 消费的事件才会传递到 `_unhandled_input`。游戏逻辑输入应放在 `_unhandled_input` 中。

**观察员须知**：
- 当玩家在 UI 界面（菜单、背包、设置）中进行操作时，注意观察游戏角色是否出现了非预期的动作。
- 如果角色在打开菜单时仍然移动或攻击，这可能是事件未被正确消费的信号。
- 重点观察菜单**关闭瞬间**的第一帧——此时事件传播路径切换，容易出现残留事件触发游戏动作。

### 2.2 GUI 遮挡场景下的 `mouse_filter` 与 `accept_event`

**引擎行为**：
- `mouse_filter` 决定控件对鼠标事件的处理方式。装饰性图标覆盖按钮时应使用 `MOUSE_FILTER_IGNORE`，否则图标会拦截点击。
- `accept_event` 可阻止事件继续传播到后续未处理的输入接收者。

**具体观察指南**：

| 场景 | 观察重点 | 异常表现 |
|------|---------|---------|
| 装饰图标覆盖按钮 | 点击图标下方按钮是否生效 | 按钮无响应，说明装饰图标拦截了事件 |
| 多层 UI 叠加 | 点击目标是否与视觉最上层一致 | 点击上层元素时触发了下层元素的行为 |
| 半透明面板 | 面板区域的点击是否穿透到游戏世界 | 面板未正确消费事件，导致游戏角色移动 |
| 输入框焦点状态 | 打字时是否触发游戏快捷键 | 键盘事件未限于输入框，传播到了游戏逻辑 |

**防坑提醒**：
- **不要**假设"看不见=不拦截"。即使控件半透明或尺寸很小，只要 `mouse_filter` 不是 `MOUSE_FILTER_IGNORE`，就会参与事件处理。
- **注意**控件的层级顺序。后添加的控件通常在视觉上层，也更先接收鼠标事件。
- 如果玩家反馈"我点的是 A 但 B 动了"，优先检查 `mouse_filter` 设置和控件层级。

### 2.3 `accept_event` 的防坑要点

- 当 GUI 控件调用 `accept_event` 后，该事件不会继续传递到 `_unhandled_input`。
- **关键陷阱**：如果某个中间控件忘记调用 `accept_event`，事件可能穿透到游戏逻辑层，导致"点了菜单但游戏也在响应"。
- 观察员遇到此类问题时，记录具体的 UI 层级和控件名称，便于开发定位。

## 3. 暂停机制：观察重点

### 3.1 `SceneTree.paused` 与物理停止

**引擎行为**：设置 `SceneTree.paused = true` 后，物理系统停止模拟。角色不会因重力下落，碰撞体不会继续推挤。

**观察员须知**：
- 暂停菜单打开后，注意观察角色是否仍在缓慢移动或漂移（物理未完全停止的异常）。
- 恢复游戏时，观察是否出现"突然弹跳"或位置偏移——这可能是物理引擎恢复时的积分误差。
- 特别关注**运动平台**场景：暂停恢复后平台与角色的相对位置应保持一致。

### 3.2 `process_mode` 的节点级控制

**引擎行为**：
- **Inherit**（默认）：跟随祖先节点状态。
- **Pausable**：随暂停停止。
- **Always**：暂停时仍然处理。

**具体观察指南**：

| 检查项 | 预期行为 | 异常表现 |
|-------|---------|---------|
| 暂停菜单按钮 | 可点击、可交互 | 按钮无响应，可能误设为 `Pausable` 或 `Inherit` |
| 暂停菜单动画 | 正常播放 | 动画冻结，节点可能继承了暂停状态 |
| 游戏世界敌人 | 完全停止 | 敌人仍在移动，可能误设为 `Always` |
| 背景特效 | 视设计而定 | 如设计要求暂停时冻结但仍在播放，检查 `process_mode` |

**防坑提醒**：
- **不要**认为"把根节点暂停就万事大吉"。子节点的 `process_mode` 如果显式设为 `Always`，则不受祖先暂停影响。
- 菜单 UI 的根节点**必须**设为 `Always`（或其祖先为 `Always`），否则暂停时菜单无法交互。

### 3.3 暂停时信号仍可触发——核心易错点

**引擎行为**：即使场景树暂停，信号仍然可以触发。这意味着：
- 计时器可能在暂停期间继续触发 `timeout` 信号。
- 网络连接状态变化可能在暂停期间触发回调。
- 全局事件总线可能在暂停期间传递消息。

**观察员必须注意**：
- **不能**把所有节点关闭当作"菜单修复"。某些逻辑通过信号在暂停期间继续执行，可能导致：
  - 暂停期间计时器到期，恢复后立即触发累积效果。
  - 暂停期间后台任务完成，恢复时产生非预期的状态变化。
  - 暂停期间的网络事件修改了游戏数据。
- 如果发现"暂停后恢复游戏立刻发生某事"，优先排查是否有信号在暂停期间被触发。

**记录模板**：
```
[暂停信号异常]
- 时间点：暂停后约 X 秒
- 现象：恢复后 [描述具体行为]
- 疑似原因：[计时器/网络/事件总线] 信号在暂停期间触发
```

## 4. 观察员操作规范

### 4.1 每场开始前的检查清单

- [ ] 确认设备已加载到正确的游戏构建版本。
- [ ] 确认引擎日志输出已开启（用于事后分析事件传播链）。
- [ ] 确认录制设备已就绪。
- [ ] 简要告知玩家本次测试目的："我们关注的是操作响应和暂停行为，不是测试关卡难度。"

### 4.2 实时记录要点

- 使用统一的观察记录表，每个验证任务标注"通过 / 异常 / 不确定"。
- 遇到异常时立即标记时间戳，便于与录像对照。
- 不要打断玩家操作，除非出现崩溃或死循环。
- 注意区分"引擎 bug"和"游戏逻辑 bug"：如果操作响应不符合直觉但不涉及输入传播或暂停机制，不属于本次测试范围。

### 4.3 每场结束后的简短访谈

建议提问：
1. "有没有哪个操作让你觉得'游戏没按我想象的方式反应'？"
2. "暂停菜单打开和关闭时，有没有注意到任何异常？"
3. "有没有遇到过点击某个按钮但触发了其他效果的情况？"

## 5. 常见误判与排除

| 表面现象 | 可能原因 | 是否属于本次范围 |
|---------|---------|----------------|
| 按键无响应 | 输入映射未配置 | 否（属于按键映射范畴） |
| 暂停后角色掉落 | `process_mode` 设置错误 | **是** |
| 点击按钮角色移动 | `_unhandled_input` 未正确过滤 | **是** |
| 菜单动画卡顿 | 性能问题 | 否 |
| 暂停恢复后敌人立即攻击 | 信号在暂停期间触发 | **是** |
| 装饰图标挡住按钮 | `mouse_filter` 未设为 `MOUSE_FILTER_IGNORE` | **是** |

---

## 6. 紧急情况处理

- **游戏崩溃**：记录崩溃时的操作序列和引擎日志最后 10 行，重启游戏继续测试。
- **死循环/软锁**：强制关闭游戏，标记该场次为"未完成"，安排补测。
- **玩家不适**：立即停止测试，提供休息，不强制继续。
