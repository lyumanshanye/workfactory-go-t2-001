# 帮团队审清网站升级方案，再交给设计和开发

你是公共服务网站的设计系统工程师。开发同事说：代码已经是2.13.3，直接装官网最新版即可。设计师还在用把tablet-lg写成800px的旧笔记。团队请你先审清楚，再决定后续怎么升级。

本项目、审批和旧稿均为原创演练；两份官方HTML是真实资料。你做的是迁移准备审查，不需要安装USWDS、编译网站或制作不存在的截图。

## 你收到什么

- project.json：代码版本、配置版本、实际使用的工具类及应提供的组件状态。
- settings.json：逐项旧配置，既有系统默认，也有团队自定义颜色。
- spacing-draft.json：设计师的旧间距表。
- component-states.json：目前真正写好的状态说明，没提供的状态不能算已完成。
- approval-events.json：谁批准了哪个方案、何时发生、何时收到。当前截点为2026-10-21 10:00 UTC；只采用发生和收到均不晚于截点、由设计负责人批准的版本，按收到时间选择最近一份。
- migration.html：官方2到3.0迁移指南；spacing.html：当前官方间距文档。当前文档不证明固定3.0包实际渲染结果。
- draft-skill.md：同事写的错误操作指南，需要改成可复用的审查技能。
- office_tools.py：可选Office排版辅助函数，不是业务依据。

## 请完成这些工作

1. 确定本轮有效方案，分开判断代码版本和配置版本。解释开发建议和晚到补签为什么不能直接用于当前审批。
2. 逐项审查全部设置：保留、改名、删除默认覆盖、替换工具模块名单，或交给设计负责人决定。不要把自定义颜色与旧默认一并删掉。若同一字段有多个历史默认变化，按目标迁移中最新适用的章节判断。
3. 按实际工具类和官方模块表列出需要的utility模块；改宽度字段名称时保留原值。共享前缀无法唯一判断时，列出待查，不猜。
4. 更正间距表，保留数字和字符串token的区别。说明旧笔记日期与后续恢复记录的关系；未知token留待确认，不能自己造一个值。
5. 列清已有和缺失的组件状态说明。给设计、工程和发布负责人分配具体补证事项。已有文字说明不等于浏览器测试已通过。
6. 修订draft-skill.md，使后续同事能处理不同版本、设置值和审批时间，不只粘贴本次答案。

## 交付什么

只在/app/output提交下面五个文件：

- review.py：接受--inputs INPUT --output OUTPUT，从输入重算，生成另外四份文件并保留同一程序。不要内嵌本次的静态结果。
- decisions.json：包含批准版本/目标/截点、代码和配置版本、逐项设置原值及处置依据、工具模块、间距原值与标称值、状态覆盖、待决自定义设置和缺失状态。compiled、browser_tested、publication_ready必须反映实际工作。input_hashes覆盖project.json、approval-events.json、settings.json、spacing-draft.json、component-states.json、migration.html、spacing.html、office_tools.py这八份复算输入。
- migration.xlsx：给人阅读的设置处置、间距校对、状态覆盖和执行交接；保留可编辑单元格，与JSON一致。
- handoff.docx：中文、不超过3页，讲清本轮结论、关键更正、为什么尚不能放行、谁来补证及复跑方法。
- SKILL.md：有name/description前置信息，可复用的审查技能；包括批准范围、版本分离、默认与自定义、间距别名、状态和补证边界。

不得修改输入、安装最新版、实际发布或伪造构建/截图/审批。缺少发布证据不影响你完成本轮能做的审查。保留真实来源及其适用范围，不把演练当真实政府项目。
